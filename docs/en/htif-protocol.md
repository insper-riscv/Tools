# HTIF: `tohost` and `fromhost`

## 1. What it is

HTIF (Host-Target InterFace) is the convention by which a program running on a RISC-V core talks to the host computer through two words of memory, with no peripheral at all. It is not part of the ISA specification or of the privileged architecture: it was born in the front-end server (`fesvr`) of Spike, the reference simulator maintained at [riscv-software-src/riscv-isa-sim](https://github.com/riscv-software-src/riscv-isa-sim), and became the standard way for a test to say it finished. `riscv-tests` and `riscv-arch-test` (ACT4) end this way, which is why the same program runs on Spike, in simulation and on the board.

## 2. The two symbols

| Symbol | Written by | Purpose |
| :--- | :--- | :--- |
| `tohost` | the program | send a command to the host, in particular the final result of the test |
| `fromhost` | the host | send a reply back to the program |

Each one is a 64-bit word, little-endian. On an RV32 core the program writes two 32-bit words, the low one at the symbol's address and the high one 4 bytes above it. Spike is not given the addresses as parameters: it looks them up in the ELF symbol table, by the names `tohost` and `fromhost`. Without the `tohost` symbol, no communication happens.

In this project the two sit side by side, with `fromhost` 8 bytes above `tohost` (`memory.tohost_addr` and `memory.fromhost_addr` in `config.yaml`).

## 3. Format of a `tohost` command

The host reads `tohost` as a 64-bit command split into three fields.

| Bits | Field | Meaning |
| :--- | :--- | :--- |
| 63 to 56 | `device` | which host device handles the command |
| 55 to 48 | `cmd` | which operation of that device |
| 47 to 0 | `payload` | the argument of the operation |

Device 0 is the system-call proxy and device 1 is the character console. When `device` and `cmd` are zero, the `payload` has two meanings, chosen by bit 0.

| Bit 0 of `payload` | Meaning |
| :--- | :--- |
| `1` | end of program; the exit code is `payload >> 1` |
| `0` | address of a block of eight words in the target's memory: the system-call number and seven arguments, which the host executes and answers in the same block |

## 4. Ending a test

A test ends by writing a `payload` with bit 0 set to `1` into `tohost`.

| Outcome | Value written | Exit code |
| :--- | :--- | :--- |
| passed | `1` | 0 |
| failed | `(code << 1) \| 1`, with `code` nonzero | `code` |

The `code` is usually the number of the check that failed, which makes a failure traceable without a debugger. While the test runs, `tohost` is 0.

Spike polls `tohost` all the time. On reading a nonzero value, it clears it to acknowledge and handles the command. On an end-of-program command, Spike exits with the test's exit code, whether it passed or failed.

## 5. `fromhost`

When the host has a reply, it writes it into `fromhost`, but only after the program has cleared the previous reply (read it and written 0). This flow control keeps a reply from overwriting another one that has not been read. A test that only finishes, like the ones in this project, never needs to read `fromhost` for this.

## 6. How this project uses HTIF

| Context | `tohost` | `fromhost` |
| :--- | :--- | :--- |
| Spike (golden generation, `spike-run`) | Spike reads it and exits with the test's code, as in section 4 | Spike's standard reply |
| Simulation (cocotb/GHDL) | the project's cocotb test watches the signals of the write to `tohost` | unused |
| Board | the host reads the low word over JTAG until bit 0 is `1` | the host writes a nonzero value to restart the core |

Two points differ from Spike.

1. **Reading over JTAG.** On the board there is no `fesvr` to decode the command. The host reads only the low word of `tohost` and considers the test finished when bit 0 is `1`. A `1` is a pass, and `(code << 1) | 1` is a failure with the `code` shown by `run` (`FAIL (code N)`).
2. **`fromhost` as restart.** After loading the next test's ROM, the host writes a nonzero value into `fromhost`. The project's boot code waits for that value and then returns to the entry point, which lets many tests run on the same bitstream without reprogramming the board.

Before each test the host zeroes both words of `tohost`, because the previous test's result is still there. Without that, the host would read a stale value and declare the new test passed before it ran.

On the program side, the `rv32_test.h` generated by `riscv-tools generate-header` provides `RV32_PASS()` and `RV32_FAIL(code)` (see [creating-a-c-test.md](creating-a-c-test.md)), plus the `RVMODEL_HALT_PASS` and `RVMODEL_HALT_FAIL(code)` names that ACT4 expects. For an assembly test, see [creating-an-asm-test.md](creating-an-asm-test.md). The module that reads and restarts through the board is described in [htif](modules/htif.md).
